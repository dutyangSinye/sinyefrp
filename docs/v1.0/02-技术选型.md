# SinyeFRP 技术选型

> 版本：v1.0  
> 日期：2026-09-23  
> 状态：已确认（用户确认采用 Go 单文件方案）

## 1. 决策摘要

SinyeFRP 管理平台采用 **Go 单文件架构**：后端使用 Go 编译为单个 Windows 可执行文件，前端 Vue 3 构建产物、`frpc.exe`、`frps.exe` 与 `LICENSE` 全部通过 `go:embed` 内嵌其中。最终交付物**不依赖任何运行时**，解压即用。

该决策不是偏好选择，而是被 `01-prd.md` 的 F18 与 KR6 强制推导出的唯一无取舍方案。

## 2. 约束与决策依据

### 2.1 硬约束

| 编号 | 约束 | 来源 |
|---|---|---|
| C1 | 交付解压即用，不要求安装 Node / Go / Python 等开发环境 | 01-prd F18、KR6 |
| C2 | 需在受限 Windows 内网分发，杀软误报不可接受 | 01-prd §5.1、§10.1 |
| C3 | 只读调用 FRP Dashboard API，不修改 FRP 内核与协议 | 00-调研 §7 |
| C4 | 需严格解析与生成 TOML，且字段必须与 FRP 0.69.x 定义一致 | 01-prd F09 / F11 / F15 |
| C5 | 需要本地持久化：设置、模板、采样快照、审计记录 | 01-prd §7.1、F08 |
| C6 | 需要流式生成 ZIP 并即时下载，不在服务端长期落盘 | 01-prd §8.5 |
| C7 | 需要 Windows 原生能力：DPAPI 加密、计划任务、服务识别 | 01-prd F13、§8.5 |

### 2.2 决策过程

- **第一层筛选（C1 + C2）**：C1 直接排除所有「解释器 + 打包器」路线。Python + PyInstaller 的产物是内网杀软的误报重灾区（C2），Node SEA 的原生 SQLite 模块需要编译链，两者都会把「解压即用」变成「解压后报毒」。候选收敛到编译型单文件方案。
- **第二层筛选（C3 + C4）**：C3 与 C4 要求管理平台只做只读采集与**受控的**配置生成，且产出的 TOML 必须被 FRP 0.69.x 接受。这里的关键判断是：**配置字段的权威性应当交给 FRP 自己，而不是复制到管理平台**。Go 与 FRP 同属静态编译、单二进制生态，管理平台可以直接以子进程方式调用 `frpc.exe verify -c` / `frps.exe verify -c` 完成校验，由 FRP 判定配置合法性——这也正是 `01-prd.md` F15 的设计。相比之下，把上游结构体复制进来（无论是手写还是引包）都只是「复制权威」，一旦 FRP 升级就可能与真实定义产生偏差。
- **第三层筛选（C5 + C6 + C7）**：Go 的 `modernc.org/sqlite` 是纯 Go 实现（无 CGO），`archive/zip` 可流式写 `http.ResponseWriter`，Windows DPAPI 可通过 `syscall` 直接调用，`go:embed` 可把前端与二进制一并打包。三项需求全部由标准库或纯 Go 依赖满足，且不破坏交叉编译能力。

结论：Go 是唯一同时满足全部 7 条约束、且不产生额外妥协的选项。

## 3. 技术栈选型

| 层次 | 选型 | 说明 |
|---|---|---|
| 语言 | Go 1.27.1 | 单文件产出，与 FRP 同生态 |
| HTTP 服务 | 标准库 `net/http`（Go 1.22+ 增强路由） | 路由需求简单，零第三方依赖即可；后续需要中间件再引入 chi |
| FRP API 客户端 | 自研薄适配层 `internal/frpapi` | 仅覆盖 6 个只读端点，自建错误分类，不引第三方 SDK |
| FRP 配置生成 | 自研 `internal/frpcfg`，受控字段子集 | 只生成表单所支持的稳定字段，不复制上游完整定义 |
| 配置校验 | 调用 `frpc.exe verify -c` / `frps.exe verify -c` | 由 FRP 自身判定合法性（严格模式），对应 F15 |
| TOML 输出 | `github.com/BurntSushi/toml` | 成熟稳定的 TOML 编解码器 |
| 持久化 | `modernc.org/sqlite`（纯 Go，WAL 模式） | 无 CGO，交叉编译无痛 |
| 数据库迁移 | 内嵌 SQL + `schema_version` 表 | 依赖最少，逻辑透明 |
| 管理员密码 | `golang.org/x/crypto/bcrypt` | 带盐哈希，符合 §8.5 |
| 敏感字段加密 | Windows DPAPI（`CryptProtectData`） | 密钥由操作系统托管并与机器绑定，无需自管主密钥 |
| 会话 | 自签 HttpOnly Cookie + 服务端 `session` 表 | 可服务端撤销，满足 F02「退出后会话失效」 |
| 部署包生成 | 标准库 `archive/zip` 流式写 | 不落盘，符合 §8.5 |
| 前端 | Vue 3 + Vite + Element Plus + ECharts | 表格、筛选、表单校验、抽屉详情组件现成，契合运维工具紧凑布局；目标浏览器为 Edge（Chromium），见 §6.1 |
| 前端内嵌 | `go:embed` | 静态资源编译进 exe |
| 交付形态 | 单个 `sinyefrp.exe` + 生命周期 PowerShell 脚本 | 满足 C1 / C2 |

## 4. 排除方案与理由

| 方案 | 结论 | 理由 |
|---|---|---|
| Python + PyInstaller | 排除 | 产物是内网杀软误报重灾区，直接违背 C1 / C2；产物体积大、冷启动慢 |
| Node.js + SEA | 排除 | 原生 SQLite 模块需要本地编译链；SEA 打包链不成熟，维护成本高 |
| Electron / Tauri | 排除 | 定位与「轻量本地运维服务」冲突；Electron 资源占用高，Tauri 引入 Rust 双语言栈 |
| .NET ASP.NET Core 自包含 | 备选，不优先 | 技术上可行，但产物体积大（60 MB 起）、构建需 SDK，且在单文件产出与资源内嵌上相对 Go 没有任何优势 |
| 纯静态 SPA + 直连 FRP API | 排除 | 会迫使浏览器持有 Dashboard Basic Auth 凭据，违背 01-prd §8.5「浏览器不直接调用 127.0.0.1:7500」 |
| fork 第三方面板（如 frp-panel） | 排除 | 已有结论，见 00-调研 §7；且最成熟候选为 AGPL-3.0 |

## 5. 交付形态与打包策略

### 5.1 内嵌决策

**采用全内嵌**：`frpc.exe`、`frps.exe`、`LICENSE`、前端构建产物、PowerShell 脚本模板全部通过 `go:embed` 编入 `sinyefrp.exe`。

| 优点 | 代价 |
|---|---|
| 版本锁定：生成包中的二进制与管理平台认知的版本永远一致 | 可执行文件体积由约 12 MB 增至约 48 MB |
| 哈希可校验：F15 要求记录文件哈希，来源固定可复现 | 每次替换 FRP 版本需重新构建 |
| 单文件交付，消除「目录不完整」这一类失效点 | — |
| 生成部署包时直接从内存读取，无需依赖外部目录 | — |

### 5.2 构建流程

```
web/                 （Vue 3 源码；依赖装在 web/node_modules，不污染全局）
  └─ vite build ──────────────┐
                              ▼
internal/web/dist/       （前端构建产物，被 //go:embed all:dist 内嵌）
internal/pack/assets/    （由构建脚本从 frp/ 复制 frpc.exe / frps.exe）
                              │
                              ▼
                     go:embed  ──►  sinyefrp.exe
```

`scripts/build.ps1` 的四步，顺序不可颠倒：

| 步骤 | 动作 | 为什么是这个顺序 |
|---|---|---|
| 1/4 | `npm run build:only` → `internal/web/dist/` | 必须在 `go build` 之前：`dist` 的内容会被 `go:embed` 编进 exe，顺序颠倒会打包出上一版前端 |
| 2/4 | 按 SHA256 比对后复制 `frpc.exe` / `frps.exe` → `internal/pack/assets/` | 哈希相同则跳过，避免每次构建都重写 36 MB |
| 3/4 | `go build -trimpath -ldflags '-s -w'` | — |
| 4/4 | 执行 `-version` 自检 | — |

两个刻意的取舍：

- **前端构建只跑 `vite build`，不跑 `vue-tsc`**（`build:only` 而非 `build`）。类型检查由开发期单独执行；挂在构建路径上会让「只改一行样式」也背上全量类型检查的代价。代价是类型错误不会阻断构建，因此**类型检查必须作为独立步骤在交付前跑一次**。
- **不清理 `internal/pack/assets/`**：`frpc.exe` / `frps.exe` 按 SHA256 判断是否需要重写，所以仓库内长期只保留一份副本；`internal/pack/assets/PLACEHOLDER.txt` 用于在尚未注入二进制时让 `go:embed` 仍能通过编译。

跳过前端构建用 `-SkipWeb`，仅在只改后端且前端产物已是最新时使用。

### 5.3 管理平台自身部署包（F18）

平台自己也要能「解压即用」地装到目标机器上，因此同一套打包能力也服务于自身：

```
bin\sinyefrp.exe pkg app -o SinyeFRP-platform-<版本>.zip
                       │
                       └─► SinyeFRP-platform-<版本>.zip
                             ├─ sinyefrp.exe              运行中的自己（含内嵌前端与 FRP 二进制）
                             ├─ config.toml               监听地址 / 数据库 / 日志 / 节点兜底
                             ├─ install.ps1 … status.ps1  六个生命周期脚本（与 frp 包同款）
                             ├─ README.txt
                             └─ SHA256SUMS.txt
```

四条必须写下来的决定：

1. **包内主程序只能是「正在运行的自己」**，因此只能在运行期生成——像 `frpc.exe` 那样编译期内嵌在数学上就不成立（自己内嵌自己）。发布流水线上跑一次 `pkg app`，产出的才是带着这一版二进制的交付件；管理台「部署包 → 管理平台自身」标签页走的是同一条代码路径（`internal/pack.BuildPlatformPackage`），因此界面上拿到的永远与当前界面同版本。读取自身二进制失败（被安全软件锁住、文件已被删除）只让那一个下载接口返回 503，不影响监控与 frp 包生成。

2. **生命周期脚本与 frp 包共用同一套模板**，差异只有三处，且全部参数化：配置参数名（frp 用 `-c`，平台用 `-config`）、是否需要预建 `data`/`logs` 并收紧 ACL、是否需要探测 HTTP 端口才算「服务可用」。为两个角色各写一套脚本，意味着修一个 bug 要改两个地方，而这两套脚本恰恰属于「改漏一处只有真装一遍才会发现」的代码。`install.ps1` 的步骤编号也据此动态计算（平台包 5 步、frp 包 4 步），避免打印出与实际步数不符的编号。

3. **脚本在运行期从 `config.toml` 解析监听端口**，而不是把生成时的端口写死（生成值只作为配置文件缺失时的兜底）。改端口是运维就地调整配置时最常见的一项；脚本若留着旧值，`status.ps1` 会一直报「端口未监听」而服务其实是好的——这种「监控喊坏了、实际是好的」比不监控更糟，它会训练运维忽略告警。

4. **`install.ps1` 会把 `data\` 与 `logs\` 的 NTFS 权限收紧到 Administrators 与 SYSTEM**。这是 DPAPI 采用**机器范围**加密（而非用户范围）的直接后果：机器范围换来「自启动与手工运行都能解密」，代价是本机任何账户都能解开密文，只能靠目录权限挡住非管理员。

计划任务名固定为 `SinyeFRP-platform`，不带变量后缀——一台机器上只应有一个管理台实例；多实例会各自向同一个 FRP Dashboard 采集，界面上的数字会来回跳。

**自启动契约**：`SYSTEM` 身份 + `RunLevel Highest` + 系统启动触发（Boot）+ 无执行时长上限 + `RestartCount 3`／间隔 1 分钟 + `StartWhenAvailable`。它由 `scripts/platform-test.ps1` 第 3b 段**回读系统里真实注册的任务对象**来守门，而不是 grep 脚本文本：「`install.ps1` 里写了 `-AtStartup`」与「系统里的任务真的具备 Boot 触发器」是两件事——`Register-ScheduledTask` 的参数一旦拼错或语义不符，脚本照样跑完并打印成功，而任务可能压根没建、或建成了一个没有触发器的空壳。同一套判据在 `lifecycle-test.ps1` 里也用在 frpc 包上，两个套件不各判各的。

首版只有这一种自启动机制：不引入 WinSW（F24 备选），也不使用根目录那份 2014 年的 `nssm.exe`（来源与签名均未核实）。两个直接后果要在交付时讲清楚：

1. **`services.msc` 里看不到这个实例**——它不是 Windows 服务。运维查状态用包内 `status.ps1`（人可读）或 `status.ps1 -Json`（机器可采集），也可以直接在任务计划程序里看。
2. **失败重启策略是兜底，不是守护进程**——它只在任务以非零码结束时按 1 分钟间隔重试，最多 3 次；次数用尽后不会再有第 4 次。重启机器才是确定性的恢复手段（`-AtStartup` 保证无需任何用户登录）。

平台包同样不落盘长期保存：与另外两个包一致，只即时生成并流式下载，生成行为写入审计与 `pkg_record`（`kind = "platform"`）。

### 5.4 敏感字段的遮蔽显示（F17）

密钥类输入（服务器 token、Dashboard 密码、客户端 token、代理预共享密钥）统一走一个组件
（`web/src/components/SecretField.vue`），显示规则只有一条：

> **未显示明文且有值时，输入框里显示的就是遮蔽串本身（只读）；显示明文后才可编辑。**

遮蔽串的写法固定为「前 4 位 + 10 个 `*` + 后 2 位」，与后端 `maskSecret` 以及
`/api/pkg/*/preview` 返回的 TOML 口径完全一致——同一个值在界面、预览、日志里必须是同一种写法，
否则管理员会以为自己面对的是不同的密钥（两套口径**刻意不统一**的只有「ZIP 内是明文」这一处，
因为客户端要能直接跑）。

四条补充规则：

1. **一个字段只允许一种遮蔽表示**。曾经的实现是 `type="password"`（渲染成圆点）
   加 `#prefix` 插槽再画一个遮蔽串——同一个值被画了两遍，两段挤在一行里。
2. **空值不锁**。还没有值时没有任何东西可遮，应当直接可编辑。
3. **从空值开始录入时自动转明文**。那是管理员自己的输入，不必再确认一次；
   否则会出现「输入第一个字符后字段被锁住」。
4. **点遮蔽串本身等于请求显示明文**，走与右侧按钮相同的确认流程，而不是让点击石沉大海。

确认不是形式主义：明文只存在于浏览器内存（服务端不落库、不回传），但界面上的明文会被旁观者、
截屏、以及「顺手 Ctrl+C 再粘贴到聊天工具」带走，复制同样走确认。

这套行为的验收不靠人眼，而由 `scripts/ui-secret-check.js` 以 DOM 断言形式纳入回归——
理由见 §8 目录结构注释：截图只能发现「崩没崩」，发现不了「值被画错」。

**弹窗化之后这里多了一条前提。** 客户端表单现在挂在 `el-dialog` 里，而 `el-dialog` 默认
teleport 到 `body`，**不在任何 `.el-tab-pane` 之内**。若断言仍按「取当前可见 tab-pane
的后代」去找字段，会一个都查不到；随后取下标 0 直接崩（这就是本次走查真正报出来的
`Cannot read properties of undefined (reading 'readOnly')`）。更危险的是写成「找不到就跳过」——
那就成了**假绿**：弹窗根本没画出来也照样判通过。因此断言改为优先定位**可见的** `.el-dialog`
作为根，并在「客户端部署包」段先点「新增客户端」按钮把弹窗打开、确认弹窗可见后再读字段。
同一条道理适用于所有「关闭即不渲染」（`destroy-on-close`）的面板：**先打开，再断言**。

## 6. 环境与配置策略

按用户确认：**开发环境与生产环境共用同一套代码，仅切换配置**。

| 项 | 开发环境 | 生产环境 |
|---|---|---|
| FRP Dashboard 地址 | `127.0.0.1:7500` | 待定（公网服务器本机回环） |
| 管理平台监听 | `127.0.0.1:7800` | `127.0.0.1:7800`（保持环回，不对外暴露） |
| 数据库 | `./data/sinyefrp.db` | 同左 |
| 日志 | `./logs/` | 同左 |

配置优先级（由低到高）：内置默认值 < `config.toml` < 环境变量 `SINYEFRP_*` < 命令行参数。所有可切换项均可在管理后台的「系统设置」中修改并持久化到 SQLite。

开发期约定：默认配置直接指向本机 `127.0.0.1:7500`，与当前 `frp/frps.toml` 中已开启的 Dashboard 保持一致，无需额外改造即可联调。

### 6.1 目标运行环境（生产）

| 项 | 开发环境（本机） | 生产环境 |
|---|---|---|
| 操作系统 | Windows 工作站 | **Windows Server 2019** |
| Web 浏览器 | 任意现代浏览器 | **Microsoft Edge（已安装）** |
| PowerShell | 5.1（系统自带） | 5.1（系统自带，无 pwsh 7） |
| 运行时依赖 | 无 | 无（单 exe 解压即用） |

**浏览器基线结论（原风险点已解除）**：Windows Server 2019 默认只带 IE11，而 IE11 不支持 Vue 3 与 Element Plus——这是「Go 单文件 + Vue 3 前端」路线唯一可能被推翻的技术风险。用户已在生产服务器安装 Edge，风险解除。

据此确定前端基线：

- **以 Edge（Chromium 内核）为唯一目标浏览器**，按现代标准开发（ES2020、CSS 变量、`fetch`、`Intl`）。
- 不引入任何 IE 兼容垫片（`core-js` 全量 polyfill、`@vitejs/plugin-legacy`），避免无谓的体积与构建复杂度。
- 保守约束仍然保留：不使用仅 Chromium 实验性开关才可用的 API；表格/表单等高频交互避免依赖最新语法糖，降低后续就地升级 Edge 版本时的回归成本。
- 交付物形态不变：前端构建产物经 `go:embed` 编入 `sinyefrp.exe`，浏览器只访问管理平台自身的环回端口，不直连 FRP Dashboard（见 §4 排除方案）。

### 6.2 脚本运行时基线

部署包内全部 PowerShell 脚本以 **Windows PowerShell 5.1** 为唯一运行时基线（生产服务器不存在 pwsh 7，也不要求安装）。由此产生三条硬性实现约束，已固化在生成端：

1. 生成的 `.ps1` 一律以 **UTF-8 with BOM** 落盘。PS 5.1 会把无 BOM 的 UTF-8 按 ANSI 代码页解析，导致中文注释乱码甚至语法报错。（BOM 与行尾的完整规则、以及「`frpc.toml` 必须无 BOM」这个反例，见 §6.8。）
2. 不使用 PS 6+ 专属语法（三元运算符、`??`、`-Parallel`、`&&`/`||` 管道链）。
3. 静态语法检查不足以替代真实安装验证——`$task` 与 `$Task` 大小写不敏感导致的变量覆盖等缺陷，只有把包真正装一遍才会暴露。因此生命周期脚本必须走 `scripts/lifecycle-test.ps1` 的真实安装回归。

### 6.3 配置路径解析基准

配置文件中 `database.path`、`log.dir`、`pack.fallback_dir` 的相对路径**一律相对配置文件所在目录解析**，程序启动时即转换为绝对路径（`internal/config` 的 `resolvePaths`）。

这条约定是被真实缺陷逼出来的：早期实现按进程工作目录（CWD）解析，而 CWD 取决于谁来拉起进程——手工执行时是 shell 的当前目录，由 Windows 计划任务（`SYSTEM` 身份、开机自启）拉起时则是 `C:\Windows\System32`。同一份配置在两种启动方式下会指向不同的数据库与日志目录，表现为「重启之后配置丢了」「数据找不到」，甚至两个实例各写一个库。以配置文件为基准后，整个部署目录搬走也不会错位。

环境变量覆盖进来的路径同样按此规则解析：只保留一个基准，避免出现「有的按工作目录、有的按配置文件」这种无法预测的组合。

### 6.4 两类「服务器信息」必须分开

平台里有两组容易被混为一谈的地址配置：

| 配置 | 位置 | 含义 | 典型取值 |
|---|---|---|---|
| 节点配置 `node.api_url` | 设置页「FRP 节点」 | 管理平台**采集状态**时访问的 frps Dashboard 地址 | `http://127.0.0.1:7500`（环回/内网） |
| 客户端接入点 | 设置页「客户端接入点」 | frpc 在目标机器上**连接 frps** 的地址与端口 | 生产：`116.169.217.89:12123` |

两者不可互相推导，原因有二：其一，Dashboard 只监听环回，外部客户端访问不到；其二，frps 前面存在 NAT 映射时对外端口 ≠ 内部 `bindPort`（生产实测：内部 7000、对外 12123），而 FRP Dashboard 的 `/api/serverinfo` 只返回 `bindPort`、不提供对外地址，因此也无法自动采集。

**auth token 由接入点统一持有**（DPAPI 加密存储），客户端包与服务端包的默认值都从这里取。这修掉了一个会直接导致部署失败的真实缺陷：早期版本每次请求各自随机生成 token，管理员先导出服务端包、再导出客户端包，两个 token 不一致，frpc 根本连不上——而单看任何一侧都是合法配置，静态检查与单包回归都发现不了。预览阶段现在会比对提交值与接入点，不一致时显式告警。

### 6.5 TOML 渲染的数字字段必须用指针

`BurntSushi/toml` 的 `omitempty` **对数字类型不生效**：其内部判定函数 `isEmpty` 只处理数组、切片、map、字符串、结构体、布尔与指针，整数没有分支、直接落到 `return false`。也就是说 `RemotePort int \`toml:"remotePort,omitempty"\`` 在值为 `0` 时仍然会被写成 `remotePort = 0`。

这不是风格问题，而是会直接产出不可用部署包的缺陷。FRP 对 http / https / stcp / xtcp / tcpmux 的代理配置做**严格解码**，配置里多出一个 `remotePort` 键就整包被拒：

```
FRP 拒绝了客户端配置: decode proxy at index 0:
unmarshal ProxyConfig error: json: unknown field "remotePort"
```

后果是「网站穿透」这类最常用的代理类型反而生成不出可用包，而 TCP 类型全都正常——只测 TCP 的回归永远发现不了。

因此：`remotePort` 只在 `tcp` / `udp` 时输出，字段类型为 `*int`（见 `internal/pack/toml.go` 的 `tomlProxy`）。**新增任何数字型的可选字段时一律先声明为指针**；`scripts\registry-test.ps1` 第 9 段（http 类型代理）是本约束的守门用例。

### 6.6 实时视图附加台账字段：内嵌提升 + 全量名称索引

FRP Dashboard 只返回 `clientID` 这类设备标识，而管理员需要看到自己填过的可读名称（如「财务部-前台机」）。这个名称只存在于本平台台账，所以 `/api/clients`、`/api/clients/{key}`、`/api/proxies` 三处由**服务端**按 `clientID` 关联后下发，不让各页面各自拼装——否则同一个 `clientID` 在不同页面可能显示成不同的名字。

两处实现选择值得记下来。

**（1）用匿名字段内嵌 `frpapi.ClientInfo` / `ProxyInfo`，而不是复制一遍字段清单：**

```go
type clientView struct {
    frpapi.ClientInfo
    DisplayName string `json:"display_name,omitempty"`
    Registered  bool   `json:"registered"`
}
```

`encoding/json` 会把匿名结构体的导出字段**提升**到外层，因此 JSON 形状与改动前完全一致：前端既有字段一个都不用动，也不存在「两份字段清单日后各自漂移」。

注意 `frpapi.ClientInfo` 有一个 `DisplayName()` 方法，而 `clientView` 又有一个 `DisplayName` 字段。Go 允许**直接字段遮蔽被提升的方法**（字段优先），编译器不报错；代价是不能再对 `clientView` 调用 `DisplayName()`，需要那段逻辑时先还原成 `frpapi.ClientInfo`。这是「编译器不拦、只能靠约定」的一处，已在 `internal/web/read.go` 就地注明。

**（2）名称索引必须走台账索引（`store.ClientMetaIndex`，早期版本叫 `ClientNameIndex`），不能用 `ListClients`：**

`ListClients` 有条数上限（`<=0` 或 `>1000` 都折回 500 条）。用它做关联，台账一旦超过 500 条，第 501 个之后的客户端就会被当成「未登记」——界面上表现为一个漂在外面的陌生 `clientID`，**且不报任何错**。`ClientNameIndex` 只取 `client_id` 与 `display_name` 两列、不设上限，专门服务于这类整表关联（客户端列表、代理列表、端口占用表）。台账读取失败时降级为「本次不展示显示名称」而不阻断列表：客户端/代理列表是管理员排查问题的主视图，不能因为一个附加字段让整页失败。

**（3）`registered` 与「名称为空」是两件事，所以单独下发一个布尔值：**

台账里允许存在「登记过但没填名称」的记录（`registered=true` 且名称为空），而 `registered=false` 说明这个客户端根本不是本平台签发的包（多为在目标机器上手工配的 `frpc`）。界面据此给两种不同提示，而不是都画成一个空单元格。未登记的客户端照常出现在列表里。

这三条都有回归守门：`scripts\registry-test.ps1` 第 10 段在真实 frps + frpc 环境下断言「名称关联正确」「代理带上名称」「删掉台账记录后清空并降级为未登记」。

### 6.7 机器人类型：只进台账与 README，不进 TOML

机器人类型（喷涂机器人 / 钢筋加工机器人 / 运输机器人 / 焊接机器人 / 其他）是**纯业务分类**，不是 FRP 的配置项。三条约束必须同时成立，少一条就出问题。

**（1）绝不写进 `frpc.toml`。** FRP 对配置里的未知字段是**严格解码、直接报错**（§6.5 记的 `remotePort = 0` 是同类事故）。让一个与连接无关的标注字段把整包变成不可用，代价完全不成比例。回归用 `tomlR -notlike '*robot*'` 兼 `-notlike '*机器*'` 双向断言，防止哪天有人「顺手」把它加进渲染器。

**（2）值域只有一个权威。** 枚举与中文标签定义在 `internal/pack/spec.go`（`RobotType`、`RobotTypeChoices()`），`internal/web` 的接口校验直接调用 `pack.ValidRobotType`，不另抄一份清单——两处清单必然漂移，届时会出现「界面能选出来的值被后端拒掉」。前端 `web/src/api/types.ts` 里的同名表只服务于渲染，注释中标明它是展示侧镜像。

**（3）空串是合法值**，语义为「未分类」。校验、存储、README 三处都要接受空串：README 用模板条件行输出，未填时整行不出现，而不是打印成 `机器人类型 : `。台账编辑按「四字段整体提交」语义实现，空串即清空——否则管理员把类型选错之后就**再也清不掉**（下拉清空后提交，值会退回旧值）。

**（4）客户端列表的类型由后端关联下发，且必须与显示名称同一次查询。** `/api/clients` 的数据来自 FRP Dashboard，它连「这台承载什么设备」的概念都没有，类型只能按 `clientID` 从本平台台账取。实现上把原来的 `store.ClientNameIndex`（clientID → 名称）升级为 `store.ClientMetaIndex`（clientID → `ClientMeta{DisplayName, RobotType}`），一次查询取三列。**不能拆成两次查询**：那样列表上的名称与类型可能来自台账的两个不同版本 —— 管理员改完类型再刷新，就会看到「新类型配旧名称」的短暂错位，而且没有任何报错。`registryNames` 保留为 `registryMetas` 的投影，供只需要名称的调用方（代理列表、端口占用）复用同一条关联逻辑。台账读不出来时整体降级（`registered=false`、类型空串），不阻断列表：实时列表是排障主视图，不能因为一个附加字段整页打不开。

**（5）「按类型分组」用类型列纵向合并实现，不用树形表格。** 候选实现有两类：树形表格（类型作父行、可折叠）与合并单元格。选后者 —— 台账表与客户端表的列都在 9 列以上，树形结构的父行只有第一列有内容、其余列全是空格，读起来像数据缺失；合并单元格保持**单一表结构**，筛选、排序、行内操作按钮全都不受影响。已知取舍：被合并的单元格在 DOM 上属于组首行，点击合并块中间部分会命中组首行的 `row-click`（客户端页据此打开详情）。类型列本身不是数据列，接受这一处歧义。

排序与合并规则统一在 `web/src/utils/robotGroup.ts`：类型按取值清单的顺序（与生成时的下拉顺序一致）、**未分类排在最后**、依赖 `Array.prototype.sort` 的稳定性保证组内维持原有次序。这份规则**只写一份** —— 两页各写一份的话，迟早出现「未分类在台账页排最后、在客户端页排中间」，而这种不一致不会有任何测试发现。筛选选项上的台数一律取**全量**口径：按筛选后的集合计数的话，筛掉一类之后其余选项立刻变 0，会被读成「那些类型下面没有设备」。

**（6）分组算错不会抛异常，因此必须单独守门。** 合并块错位、筛选计数变 0、`span-method` 的列下标写错导致整列内容消失 —— 这些全都既不报错、页面也照样好看，`vue-tsc` 与截图都发现不了。因此新增 `scripts/ui-robot-group-check.js` 并入走查段：脚本在浏览器里自己生成三个带类型的客户端包（两个同类型 + 一个另一类型），再读 DOM 断言表头、分组台数、合并块的 `rowspan`、筛选后的行数与筛选计数。**必须先造数据**：空台账下这些断言会全部假绿（「找不到分组」与「分组是对的」在文本上区分不开）。另外，走查实例没有配置客户端接入点，`defaults` 返回的 `server_addr` 是空串而 spec 校验要求它非空，造数据时要显式兜一个地址，否则三次生成全是 400。

**迁移（v3）**：`client_registry` 增加 `robot_type TEXT NOT NULL DEFAULT ''`。已发布的 v2 不许改，所以走 `ALTER TABLE ... ADD COLUMN` 而不重建表；默认空串即「未分类」，老记录无需回填。这条升级路径回归覆盖不到（回归每次都用新库），因此另外做了一次「程序建全库 → 摘掉 `robot_type` 列与 v3 迁移记录 → 用新版启动」的演练，确认 `ALTER` 在真实老库上能跑通且健康检查通过。

### 6.8 包内文本的编码与行尾：按「谁读它」分开判定

行尾与 BOM 是两件独立的事，必须分别判定——合成一个开关，迟早会顺手把一半正确的做法加到另一半上。

**行尾：全部文本文件一律 CRLF（含 `.ps1`、`.toml`、`README.txt`）。**
理由是记事本。Windows Server 2019 自带的老版记事本在另存时会把裸 LF 全量改写成 CRLF，而包内 `config.toml` 恰恰是运维唯一会亲手打开编辑的文件（改端口、改节点名、改 Dashboard 地址）。出厂若是裸 LF，「打开看了一眼、顺手保存」就足以让文件哈希变化，进而触发安装脚本的校验提示，把人引向一个不存在的故障。

**BOM：不能一刀切，判据是这份文件由谁的解析器读。**

| 文件 | BOM | 原因 |
|---|---|---|
| `*.ps1`、`README.txt` | **必须带** | PS 5.1 会把无 BOM 的 UTF-8 按 ANSI 代码页解析，中文注释乱码甚至语法报错 |
| 平台 `config.toml` | **必须带** | 整篇中文注释，运维用记事本打开；`internal/config`（BurntSushi）容 BOM |
| `frpc.toml` / `frps.toml` | **绝不能带** | FRP 0.69.0 的 TOML 解析器遇 BOM 直接报 `toml: line 1, column 1: toml: invalid character at start of key: ï`，退出码 1，`frpc`/`frps` 完全起不来 |

这张表是**实测**得来的，不是读文档得来的：把同一份配置按「行尾 × BOM」四种组合各跑一次 `frpc verify -c`，只有带 BOM 的两种失败（`.workbuddy/test/verify-toml-variants.ps1`）。同时它也确认了 **FRP 对 CRLF 完全无害**——这一点很关键，否则「统一成 Windows 原生形态」这个动作会连行尾一起被误判。写在这里是因为「顺手把 BOM 统一加上」看起来只会让事情变好，代价却是整个包都跑不起来。

归一化只有一处实现：`internal/pack/builder.go` 的 `assemble()`，默认值、预览、下载三条出站路径全部经它。分散到各模板里改，迟早漏掉一个——而漏掉的那个症状是「包装不上」而不是「格式不对」，很难查回来。

### 6.9 安装时的哈希校验：两级判定

| 对象 | 不一致时 | 理由 |
|---|---|---|
| 主程序（`frpc.exe` / `frps.exe` / `sinyefrp.exe`） | **中止安装**（退出码 12） | 它是包的代码，出厂后不该被人动过 |
| 配置文件（`frpc.toml` / `frps.toml` / `config.toml`） | **仅提示，继续安装** | 端口、节点名、Dashboard 地址本就要按目标环境改，改完再装是标准流程 |

这条不对称是刻意的，而且是从「逃生口的存在方式」倒推出来的：若把配置改动也判死，运维唯一的出路就是加 `-SkipHashCheck`，而那个开关会把主程序的校验一起关掉——等于为了改一个端口而放弃对代码的校验。默认路径必须是能正常走通的，否则所谓的强制校验只会训练人绕过它。

`-SkipHashCheck` 保留，但提示语明确写出它会同时跳过主程序校验。守卫分两层：`platform-test.ps1` 两侧都断言（主程序被改 → 12；配置被改 → 装成功且输出含提示），`verify-pack-integrity.ps1` 则复核包内脚本确实带上了这两条判定。

### 6.10 监听地址的两种含义：绑定地址 ≠ 可访问地址

`config.toml` 的 `listen_addr` 可以按需改成 `0.0.0.0`（公网直接访问管理台），但脚本不能再把 `127.0.0.1` 当访问地址打印出来，否则运维照着一个只有本机能用的地址去浏览器里试，必然失败。

因此生命周期脚本在运行期解析 `listen_addr`（`Get-ServiceAddr`），并分两种情形给出地址（`Get-AccessURL`）：非通配地址直接用；是 `0.0.0.0` / `::` 这类**通配地址**时改用本机第一个 IPv4 地址——通配地址是绑定用的，拼进 URL 打不开。

监听超出环回时（`Test-PublicBind`）额外打印两行提示：本界面是纯 HTTP，管理员密码与会话 Cookie 会明文经过网络，请确认防火墙入站规则的来源已限制到固定 IP。脚本不阻止这种配置（生产上确实可能配合安全组使用），但必须让运维看见代价。

### 6.11 双击安装入口：只提权与转发，不实现逻辑

现场交付的对象是设备现场人员，不是运维。原来的安装路径要求他：打开 PowerShell → 右键「以管理员身份运行」→ `cd` 到解压目录 → 敲 `.\install.ps1`，还得先撞过 PowerShell 的执行策略。README 里那两条「无法将 install.ps1 项识别为 cmdlet」「禁止运行脚本」的问答，本身就是这条路径门槛过高的自证。

包内因此新增双击入口 `一键安装.bat`（F21）。三条设计约束：

1. **不改变手动路径的行为。** `install.ps1` 新增两个开关：`-Elevate`（非管理员时用 `Start-Process -Verb RunAs` 弹 UAC 把自己重跑一遍，并带内部标记 `-Elevated` 防止无限弹框）与 `-Pause`（装完停屏；否则双击的人只看到黑窗口一闪）。**不传这两个开关时行为与从前完全一致** —— 仍是退出码 10、仍不弹框。运维脚本、自动化流水线、监控采集都依赖这个契约：照顾双击路径，不能以把无人值守的安装挂死在 UAC 弹框上为代价。
2. **`.bat` 的编码要求与 `.ps1` 恰好相反。** cmd.exe 用控制台代码页（简体中文为 CP936）解析 `.bat`，所以入口内容必须**纯 ASCII** —— 面向人的中文提示一律交给它调起的 PowerShell 输出（`.ps1` 是 UTF-8 with BOM，中文一定正确）。并且**绝对不能带 BOM**：cmd 会把 BOM 当成命令的一部分，首行报 `'ï»¿@echo' 不是内部或外部命令`，双击彻底没反应、不留任何日志。`normalizeText` 为此给 `.bat` 单开一档「去 BOM + CRLF」，并排在那条会加 BOM 的 `isTextName` 分支**之前**（顺序即保证）。
3. **入口里不复制任何生命周期逻辑。** 只转发，内容里不出现 `Register-ScheduledTask`。同一件事有两处实现，迟早改漏一处，而这类漏改只有真装一遍才会暴露。守门断言直接查入口内容里有没有 `Register-ScheduledTask`。

`-Pause` 另有一处必须的防呆：`[Console]::IsInputRedirected` 为真时跳过等待。否则「双击时舒服」换来的是「任何把标准输入接走的调用方永久卡在 `Read-Host` 上」—— 而回归套件调用被测脚本的方式正是这一种。

入口用中文名是取舍：辨识度换编码风险。`archive/zip` 对非纯 ASCII 的条目会自动写 UTF-8 标志位（general purpose bit 11），资源管理器与 7-Zip 都能正确解出；个别老解压工具仍可能解成乱码，所以 README 专门写了「文件名显示成乱码怎么办」（改用资源管理器「全部解压缩」或 7-Zip 重解）。这条风险必须写进交付说明，不能留给现场猜。

### 6.12 本地端口：FRP 不返回，只能由台账关联

看端口只关心两件事：**目标机器上是哪个端口**（本地），**外面从哪个端口进来**（远端）。原先四处端口展示（代理列表、客户端详情、客户端台账、端口占用总览）都只有远端端口 —— 代理页那一列甚至标着「本地 → 远端端口」，内容却是「远端 16001 ← 127.0.0.1」，把本地 **IP** 摆在了本地端口的位置上。

根因在 FRP：Dashboard 的代理 `conf` 只给 `localIP` 与 `remotePort`，**不返回 `localPort`**（03-frp-api-contract §4-⑦）。这不是「多取一个字段」能解决的。

因此本地端口的唯一来源是本平台台账：`client_port` 表在建包时就逐条记下了本地端口，实时视图按 **`(clientID, 代理短名)`** 关联补齐（新增 `store.ClientPortIndex`，与 F19 的名称、F20 的类型同源同路径）。三个必须守住的点：

1. **关联键是代理短名，不是完整名。** 台账里存的是表单填的短名，而 FRP 返回的 `Name` 是 `user.proxyname`，关联前必须经 `shortProxyName` 拆开。键写错的症状是本地端口**恒为 0**，而接口 200、页面正常、不报任何错 —— 这类「静默恒零」是本功能最大的风险，故接口层直接断言取回的值等于建包时填的值（正反两向各一条）。
2. **必须显式下发「是否登记」。** 沿用 `registered` 的做法，`proxyView` / `portOwnerView` 各带一个 `local_port_known`。**不允许前端用 `local_port > 0` 代替**：包不是本平台签发的（别处手工配的 frpc）就永远关联不上，那时要显示「未登记」/「—」；显示成 0 会被读成「本地端口是 0 号」——而 0 是非法端口号（`checkPort` 要求 `1-65535`）。
3. **读不出台账就降级，不阻断列表。** 与名称、类型同一套语义：客户端与代理列表是管理员排查的主视图，不能因为一个附加字段整页报错。代价是「台账读失败」与「这条代理没登记」在界面上不可区分，所以两者都留了日志。

本地端口**不参与冲突判定**：它属于目标机器自己的地址空间，两个客户端都用 3389 是正常的。台账页端口表的副标题据此写明「本地端口只作比对，不参与保留判定」，免得读者以为它也像远端端口那样被保留。

交付层面另有一处结构性改动：`clientDetailResponse.Proxies` 原先直接下发 FRP 原始结构（当时的理由是「它们同属一个客户端，重复显示名称没意义」）。本地端口是**逐条代理**的属性后，这条理由不再成立 —— 原始结构根本给不出这个字段。故改为 `[]proxyView`；它是 `ProxyInfo` 的超集（匿名字段内嵌提升），JSON 形状向后兼容，也就不必为详情页再定义第三个近似类型。

### 6.13 改包：用台账重建出包表单（F27）

「重新生成一个已签发设备的部署包」此前只有一个办法：把当初的表单重填一遍。容易出错且不必要 —— 台账里那份数据正是当初的输入。

**（1）「编辑旧包」在物理上不存在，草稿是唯一形态。** 部署包 ZIP 从不落盘、服务端也不保留签发密钥（01-prd §8.5），所以拿不到旧包。能重建的只有输入，而输入的唯一去处是台账。于是 `GET /api/registry/clients/{id}/spec` 返回一份**完整的 `ClientSpec`**（不是半成品表单结构），直接喂给原有的签发接口。新包与旧包共用同一个 `clientID`，目标机器上覆盖安装即可。这样做的好处是：**改包没有第二条签发路径** —— 冲突拦截、FRP 校验、审计记账、台账更新全部照旧，不存在「改包专用的那条路忘了拦冲突端口」这种分化。

**（2）台账必须存够下一次出包所需的输入 —— 于是有了迁移 v4。** `client_registry` 增加 `platform` 列。它之所以必须落库，是因为平台决定了**包能不能装上**：给 Linux 盒子出 Windows 包，安装脚本不报错，症状要等现场上线才浮出来。空串表示「未记录」（v4 之前签发的包），界面按默认平台展示，但**首次改包必须告警让管理员确认**，不能替他默认 —— 默认值在这里猜错的代价远高于让他点一下下拉。

**（3）这条值最容易被一次无关操作清掉。** 台账编辑是**整体替换**语义（`UpdateClient` 按传入结构体覆盖），调用方漏传 `platform` 就把它清成未记录。事故链是：某天点了一次「停用」→ 几周后给这台 ARM 盒子改包 → 产出 Windows 包，而没人会怀疑当初那次停用。三条路径（停用、启用、改类型）都在 `registry-test.ps1` 里各有一条断言：**先把平台写成 `linux-arm64`，走完该动作再回读应仍是 `linux-arm64`**。这类保护只能靠显式断言 —— 少传几个字段的编辑请求在今天完全合法，后果却要几周后才浮出来。

**（4）表单里的值必须分成两类，且界面不许把它们混在一起展示。** 台账里有的（clientID、名称、类型、平台、各代理两端端口）是真实还原；台账里没有的（连接 token、日志级别、HTTP 域名与路由、STCP/XTCP 访问密钥、每条代理的本地 IP）由默认值补齐。**第二类的危险在于它长得和第一类一模一样** —— 一行表格里填好了两个数字，看不出来源。故后端如实回两份元数据：`defaults_applied`（整包级字段清单）与 `proxy_defaults`（逐条代理列出缺哪些字段），前端把它们渲染成一块「这些不是原包的样子」的提示条。逐条代理的清单还只列**这条代理类型用得上的**字段：给 tcp 列 `custom_domains` 是噪音，给 http 不列才是漏。

**（5）连接 token 永远取当前接入点，绝不试图还原旧包的。** 一是旧包的 token 从未留存；二是就算留着也必须与接入点一致 —— 两端 token 不一致时目标机器上的 frpc 连不上，而这个故障在管理台这一侧看不到任何痕迹 —— 这与 §6.4「auth token 以接入点为唯一权威」是同一件事。接入点读不出来时（典型是 DPAPI 密文随 SQLite 换了机器）降级为空值让管理员手填，而不是把整台设备的改包入口废掉。

**（6）冲突判定要把「这台设备自己占用的端口」排除在外，否则改包直接不可用。** 冲突检查有两条调用路径：补录走 `conflictsFor(ctx, wanted, "")`（新记录还不存在，任何既有占用都算冲突），改包走 `conflictsFor(ctx, wanted, spec.ClientID)`。漏掉 `ownerClientID` 的后果不是告警而是功能消失 —— 改包的典型动作就是「同一台设备、同一批端口，再出一版」，自己也挡的话首次签发之后再也发不出第二版。这条此前已经顺带验证过一次（F19 的「同 clientID 重新生成不算冲突」），但那时它是**顺带效果**；现在它是改包唯一的路径，回归里保留了正向（200）与反向（换一个 clientID 撞同一端口 → 409，且 details 点出占用方 clientID）两条断言。

**（7）跳转只带台账 id，不带任何敏感值。** 台账页「生成包」入口跳 `/packages?from=<id>`；spec 里含 token，塞进查询串等于把密钥写进浏览器历史、截图与 Referer。目标页按 id 自己取草稿，**取到后再打开弹窗**（顺序反了会先闪一版全新默认值），取不到就退回「新增」并提示 —— 那条记录可能刚被删，而管理员的意图不该被这个失败挡死。

**（8）改包链路里「静默失效」的点不止一处，故这次补了 19 条断言。** 平台写丢（第 3 条）、平台被整体替换清成空（同上）、草稿的 clientID 取错（后果是包挂到陌生设备名下，界面上看不出来，只是台账多一行）、缺项被默认值悄悄补齐而界面不说（第 4 条）、token 还原自旧值（连不上且无告警）、自己的端口挡住自己（第 6 条）—— 它们全都不报错、页面也都好看。
