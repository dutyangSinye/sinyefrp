# SinyeFRP 管理平台产品需求文档

> 版本：v1.0  
> 日期：2026-09-23  
> 状态：草稿（待确认）

## 1. 摘要

SinyeFRP 是部署在 `frps.exe` 外层的本地管理平台。它不修改 FRP 协议或核心程序，而是读取 FRP 0.69.0 自带的 Dashboard API，集中展示服务器、客户端和代理状态，并根据表单自动生成可直接交付的 Windows 客户端或服务器端部署包。

首版面向自行维护一台 Windows FRP 服务器的管理员，重点解决三个问题：不知道哪些客户端在线、手写 TOML 容易出错、Windows 开机自启动部署步骤不统一。

## 2. 联系人与角色

| 角色 | 负责人 | 职责 |
|---|---|---|
| 产品负责人 / 验收人 | 用户 | 确认范围、交互和最终可用性 |
| 系统管理员 | 用户或授权运维人员 | 配置 FRP 节点、生成部署包、查看状态 |
| 设计与开发 | Codex | 按已确认文档实现、测试和打包 |
| 被管理客户端用户 | 内网 Windows 设备使用者 | 运行管理员提供的安装脚本，不接触管理后台 |

## 3. 背景与问题

### 3.1 当前情况

- 已有 Windows 版 `frps.exe` 和 `frpc.exe`，版本均为 `0.69.0`。
- `frps.toml` 已开启仅监听 `127.0.0.1:7500` 的 Dashboard/API。
- FRP API 可以返回客户端身份、主机名、IP、版本、在线状态、连接时间、代理、流量和连接数。
- 当前仍需人工编辑 TOML、复制程序和编写启动脚本；不同客户端容易出现名称、端口和路径不一致。

### 3.2 核心问题

1. 管理员需要打开多个页面或查看日志，才能判断客户端是否在线、代理是否正常。
2. 手工制作客户端部署目录容易遗漏配置、写错端口或重复使用代理名称。
3. 双击批处理只能临时启动，无法统一解决管理员权限、开机启动、日志、状态查询和卸载。
4. FRP 重启后部分内存统计会丢失，单靠内置 Dashboard 不适合保留管理记录。

### 3.3 为什么现在可以做

FRP 0.69.0 已提供 `/api/clients`，可以直接查看所有注册过的客户端，包括没有代理的客户端。首版因此可以采用官方接口完成只读监控，无需修改 FRP 或先部署 Server Plugin。

## 4. 目标与成功标准

### 4.1 产品目标

- 一个页面看清服务器是否正常、客户端是否在线、代理是否可用。
- 通过表单生成标准部署包，避免管理员手写 TOML 和脚本。
- 客户端用户以管理员身份运行一次安装脚本后，FRP 能在 Windows 开机时自动启动。
- 管理平台与 FRP 解耦，升级或关闭管理平台不影响已有 FRP 转发。

### 4.2 可验收的关键结果

| 编号 | 关键结果 | 验收口径 |
|---|---|---|
| KR1 | 监控数据准确 | 接入真实 FRP 0.69.0 后，服务器、客户端和代理核心字段与官方 API 一致 |
| KR2 | 部署成功 | 使用系统生成的客户端 ZIP，在全新 Windows 测试环境中 10 分钟内完成安装并出现在客户端列表 |
| KR3 | 自启动可靠 | Windows 重启后，无需登录桌面，frpc/frps 自动运行并能恢复连接 |
| KR4 | 脚本可逆 | 安装脚本可重复执行；卸载脚本移除自启动项，但默认保留配置和日志以便恢复 |
| KR5 | 故障可判断 | FRP API 不可达、认证失败或配置错误时，界面明确显示原因，不把“未知”错误标记为客户端离线 |
| KR6 | 交付可直接使用 | 最终提供已经构建和打包的管理平台及部署包，不要求用户自行编译源码 |

## 5. 目标用户与核心场景

### 5.1 目标用户

- 主要用户：维护一台 Windows FRP 服务器、管理少量到数百个 Windows 客户端的管理员。
- 次要用户：拿到客户端部署包并执行安装的现场人员。
- 使用约束：首版管理平台和 frps 部署在同一台 Windows 主机；管理后台只供受信网络内的管理员访问。

### 5.2 用户场景

| 优先级 | 场景 | 触发 | 用户操作 | 期望结果 |
|---|---|---|---|---|
| P0 | 查看运行状态 | 需要检查内网设备是否仍在线 | 登录管理台并打开总览或客户端列表 | 看到服务状态、在线/离线数量、最后连接时间和异常原因 |
| P0 | 新增客户端 | 一台新 Windows 设备需要接入 | 填写设备名称和代理信息，生成并下载 ZIP | 解压后以管理员身份运行安装脚本即可上线 |
| P0 | 部署新服务器 | 新 Windows 主机需要运行 frps | 填写监听端口和管理设置，生成服务器 ZIP | 安装脚本创建自启动任务并启动 frps |
| P0 | 排查代理 | 客户端在线但业务无法访问 | 打开客户端详情查看关联代理、远端端口、连接数和流量 | 能区分客户端离线、代理离线、端口配置问题和 API 故障 |
| P1 | 回看异常 | 客户端曾短暂掉线 | 查看事件和历史趋势 | 找到上下线时间及流量变化 |

## 6. 价值主张

- 相比 FRP 内置 Dashboard：增加统一登录、易读的客户端视图、持久化管理记录和部署包生成。
- 相比手写配置：表单校验代理名称、地址和端口，自动生成唯一 `clientID`，降低复制错误。
- 相比完整第三方面板：保留官方 FRP 二进制，部署轻、边界清晰，不引入多租户、计费和组网等无关复杂度。
- 相比只提供一个批处理：生成完整的安装、卸载、启动、停止、重启和状态查询脚本，且支持开机自动运行。

## 7. 解决方案与功能清单

### 7.1 产品结构

```text
管理员浏览器
    |
    v
SinyeFRP 管理服务 ---- SQLite（设置、模板、采样与审计）
    |
    +---- FRP Dashboard API（127.0.0.1:7500）
    |
    +---- 部署包生成器
              |
              +---- Windows frpc ZIP
              +---- Windows frps ZIP
```

管理服务是 FRP API 凭据的唯一持有方，浏览器不直接请求 FRP Dashboard。即使管理服务停止，已经运行的 `frps.exe` 和 `frpc.exe` 仍继续工作。

### 7.2 P0 功能

| F01 | 首次初始化 | 首次启动创建管理员账号，配置本机 FRP API 地址、用户名和密码 | 未初始化不能进入后台；密码加密哈希保存；FRP 凭据不以明文返回前端 |
| F02 | 管理员登录 | 使用账号密码进入后台并安全退出 | 错误密码不给出账号是否存在；连续失败有限速；退出后会话失效 |
| F03 | FRP 节点连接 | 保存并测试一个 frps 节点的 API 配置 | 能区分连接失败、超时、401、版本不兼容和成功；首版只允许一个启用节点 |
| F04 | 总览 | 展示 FRP 版本、运行状态、客户端数、代理数、当前连接数和流量 | 数据包含采集时间；API 故障时显示“状态未知”和上次成功时间 |
| F05 | 客户端列表 | 展示名称/标识、主机名、IP、版本、在线状态、首次/最近连接时间 | 支持关键词、在线状态筛选和手动刷新；数据与 `/api/clients` 一致 |

| F26 | 本地端口展示 | 所有展示端口的地方（代理列表、客户端详情、客户端台账、端口占用总览）同时给出**本地端口**，而不只是远端端口 | 本地端口属于目标机器自己的地址空间，**不参与端口冲突判定**、可与其他客户端重复；FRP Dashboard 的代理 `conf` **不返回** `localPort`（只有 `localIP` 与 `remotePort`，见 03-frp-api-contract §4-⑦），因此实时口径的本地端口由后端按 `(clientID, 代理短名)` 从台账关联补齐；**未登记时显示「未登记」/「—」，不得显示 0**（0 是非法端口号，显示出来只会让人以为程序算错）；台账读不出来时只降级为不显示本地端口，不影响列表本身 |
| F27 | 按已签发客户端改包 | 从客户端台账一条记录出发，用台账里的内容重建出包表单，管理员改完后生成一个**新**包（同一 `clientID`），目标机器覆盖安装即可 | 台账页每行提供「生成包」入口（跳到部署包页并自动打开预填表单）；表单里的值分两类且必须在界面上分开标识：**台账里有的**（`clientID`、显示名称、机器人类型、目标平台、每条代理的两端端口）是真实还原，**台账里没有的**（连接 token、日志级别、HTTP 域名与路由、STCP/XTCP 访问密钥、每条代理的本地 IP）由默认值补齐，逐项列出而不是笼统提示；台账未记录目标平台时按默认平台预填并给出告警由管理员确认；连接 token **永远取自当前客户端接入点**，不试图还原旧包的；除外之外一切通路仍走 F09/F10 的签发路径：端口冲突照样拦、证照照样审计、台账照样更新 |

## 8. 部署包业务规则

### 8.1 客户端身份

- 每个新部署包必须具有唯一 `clientID`，用于跨重连识别同一台设备。
- 显示名称供管理员阅读，允许中文；写入 FRP 的代理名和任务名使用安全化后的 ASCII 标识。
- 同一部署包复制到多台机器会造成身份冲突，生成页面和 README 必须明确提示“一台设备一个包”。
- 每次签发的 `clientID` 与显示名称都记入「客户端台账」（见 8.6）；台账里名称与备注可改，`clientID` 不可改。
- **显示名称必须贯通到所有列出客户端或代理的地方**：客户端列表与详情、代理列表及其「所属客户端」筛选、台账页、台账与实时两张端口占用表。关联统一由后端按 `clientID` 完成，不允许各页面各自拼装 —— 否则同一个 `clientID` 在不同页面可能显示成不同的名字。
- FRP 里可能出现台账没有记录的客户端（多为在目标机器上手工配置的 `frpc`）。这类客户端必须如实标注「未登记」并说明可能来源，**不能画成一个空格** —— 空白会被读成“加载失败”或“这台机器没填名字”。因此「台账里有记录但名称为空」与「压根没登记」是两种状态，界面分开表达。

### 8.2 端口与代理

- TCP/UDP 端口范围为 `1-65535`；系统保留或已占用端口给出警告。
- 远端端口在同一个 frps 上是**全局资源**：两个 `clientID` 占用同一端口后，后注册的那个代理会被 FRP 拒绝，而失败现象只出现在目标机器的 `frpc` 日志里，离管理台很远。因此端口冲突必须在生成部署包时就拦下。
- 冲突判定分**两个口径**，不合并、不互相替代：
  - **台账口径**：本平台已签发过的客户端所占的端口。它包含「已签发但还没安装」的情况，实时接口看不到。
  - **实时口径**：FRP Dashboard 此刻真实在线的代理端口。它包含「在别处手工配置、不在本平台台账里」的情况，只能靠改端口规避，台账里没有可释放的记录。
- 同口径判定规则：同一 `clientID` 重新生成不算冲突（改代理后重新出包是必须放行的路径）；台账里已停用（`retired`）或已删除的记录不占用端口。
- 拦截动作：下载部署包时若存在冲突则拒绝（HTTP 409），并逐条给出占用方名称、`clientID`、占用端口与处理建议（改端口，或先到台账停用/删除占用方）。
- 预览接口不拦截，只把冲突作为 `blocking` 列出：管理员必须仍能看到完整 TOML，否则无法判断该把端口改成多少。
- 由于其他客户端可能在生成后抢占端口，安装时仍以 FRP 返回结果为最终判断。
- **每个端口都要同时给出本地与远端两个值**（F26）。本地端口属于目标机器自己的地址空间，两个客户端都用 3389 是正常的，**不参与冲突判定**；台账页端口表的说明文字要写明这一点，否则读者会以为本地端口也被保留。FRP Dashboard 的代理 `conf` 不返回 `localPort`（03-frp-api-contract §4-⑦），所以实时口径的本地端口由后端按 `(clientID, 代理短名)` 从台账关联补齐；补不到时显示「未登记」/「—」，**不得显示 0** —— 0 是非法端口号，显示出来只会让人以为程序算错。

### 8.3 自启动脚本

- P0 使用 Windows 原生 PowerShell 计划任务，不依赖当前目录中的旧 `nssm.exe`。
- 任务以 `SYSTEM` 身份在系统启动时运行，工作目录固定到部署目录，标准输出和错误写入日志目录。
- 安装脚本先检查管理员权限、二进制、配置和哈希，再创建或更新任务。哈希校验分两级：主程序与包内记录不一致时中止安装（包不可信）；配置文件不一致时只提示并继续——按目标环境改配置（端口、节点名、Dashboard 地址）是部署常态，不该被校验挡住。跳过校验的开关必须显式使用，且提示语要写明它连主程序校验一起跳过。
- 卸载默认停止任务并删除自启动项，保留 TOML 和日志；提供明确参数才删除数据。
- 脚本必须支持路径包含空格；PowerShell 执行策略受限时给出可复制的解决命令，不静默绕过安全策略。
- 提供可直接双击的安装入口（`一键安装.bat`，F21）：自动请求管理员权限后完成安装，让不熟悉 PowerShell 的现场人员也能装起来。入口只做「提权 + 转发给 `install.ps1`」两件事，**不复制任何安装逻辑**；手动的 `.\install.ps1` 行为保持完全不变，非交互调用缺权限时仍以退出码 10 收场 —— 不会为了照顾双击路径而弹一个 UAC 框把无人值守的安装挂死。入口自身显式带 `-ExecutionPolicy Bypass`（用户双击即等于主动运行这个包），但**不修改机器上的长期执行策略**；手工调用脚本被执行策略拦住时，仍按上一条给出可复制的解决命令。

### 8.4 监控状态

- `在线/离线` 以 `/api/clients` 返回的 `online` 为准。
- API 不可达时节点状态为 `未知`，不能把全部客户端批量标为离线。
- 页面显示数据采集时间；超过 30 秒未成功采集时标记为过期。
- 首版保留最后一次成功快照，不承诺长期趋势；完整历史趋势属于 P1。

### 8.5 凭据与下载

- 新服务器包使用密码学安全随机数生成 FRP token 和 Dashboard 密码。
- ZIP 包含可用密钥，属于敏感文件；服务端只即时生成并流式下载，不长期保存完整 ZIP。
- SQLite 中需要保存的外部凭据必须加密保存；管理员密码只保存带盐哈希。
- 所有管理接口默认同源访问，不允许浏览器直接调用 `127.0.0.1:7500`。

### 8.6 客户端台账

- 每次成功生成客户端部署包时，以 `clientID` 为唯一键登记一条台账：显示名称、接入地址、状态（启用/停用）、备注、签发次数、首次与最近签发时间，以及包内每个 TCP/UDP 代理占用的远端端口。
- 端口占用按「本次生成的完整结果」**整体替换**，不是累加：包里去掉了某条代理，对应端口必须立即释放，否则会被一条已不存在于任何包里的记录永久锁住。
- 停用（`retired`）或删除台账记录即释放其占用端口。重新启用时要做一次反向冲突校验——否则会出现两个「启用」状态的客户端占用同一端口。
- 删除台账记录不会影响目标机器上正在运行的 `frpc`：管理平台不反向控制已部署的客户端，删除只表示「本平台不再为它保留端口」。
- 重新生成同一 `clientID` 的包时，台账自动恢复为启用、累加签发次数，已填写的说明与备注保留。
- 台账是「本平台的签发历史」，与「FRP 此刻的在线状态」是两件事，界面必须分开呈现；同时要标出「台账里有、FRP 里未见」这类异常（包已签发但从未上线）。
- **台账页必须能回答「现在通不通」**，因此要**同时下发两个状态**：`seen_in_frp`（FRP 快照里出现过没有，**含已断开但尚未被 FRP 清理**的客户端）与 `online`（此刻在线）。界面据此呈现三态：在线 / 离线（连过，后来断了）/ 从未上线；尚未成功采集时显示「—」。只给 `seen_in_frp` 不给 `online`，「离线」就会被显示成「没装过」，而两者处置方式完全不同 —— 前者查网络、frps 与目标机器上的 frpc，后者要去现场装包。「从未成功采集」也必须显示「—」而不是「没装」，否则会把「Dashboard 连不上」误报成「客户端全都没上线」（同 §8.4 的语义）。

### 8.7 机器人类别

- 生成客户端部署包时，可标注**这台设备承载的机器人类型**，取值固定为：喷涂机器人、钢筋加工机器人、运输机器人、焊接机器人、其他。不给自由文本 —— 同一类设备被写成多种叫法后就再也统计不出来。
- 该字段**可留空**，留空即「未分类」。留空是合法状态，不阻塞生成；界面上呈现为「未分类」，而不是画成一个空格。
- 机器人类型是**纯业务分类**：只进客户端台账，并随包写入包内 `README.txt`（写中文全称）。**不写入 `frpc.toml`** —— FRP 对配置中的未知字段是严格解码直接报错（同类事故见技术选型 §6.5），一个与连接无关的标注字段没有理由让整包不可用。
- 它**不参与端口占用判定**，也不是身份的一部分：同一 `clientID` 换成另一种机器人类型重新出包不算冲突，`clientID` 保持不变。
- 台账页可随时修改或清空类型；改动只影响**下次生成**的包，已签发的旧包不会被追溯修改。
- **两处都要展示，并按类型分组归拢**：客户端台账（签发记录）与客户端（FRP 实时列表）都展示机器人类型，且同类型的行在「机器人类型」列上纵向合并成一个格子，组内标出台数（只有 1 台时不标 —— 那是噪音，没有信息量）。两处都提供按类型筛选，选项上带各类台数。
- 筛选选项的台数一律是**全量口径**，不随当前筛选变化：按筛选后的集合计数的话，一旦筛了某一类，其它选项立刻变成 0，会被读成「那些类型下面没有设备」。
- 客户端列表的类型**由后端按 clientID 关联台账下发**，与显示名称走**同一条路径、同一次查询**：FRP Dashboard 根本没有这个概念，前端也拿不到台账全量。关联读不出来时降级为「未分类」并保持 `registered=false`，不阻断列表本身。
- 排序规则固定：具体类型按取值清单的顺序（与生成时的下拉顺序一致），**未分类排在最后**（它是兜底归类，不该占住列表开头）。这条规则在两个页面共用同一份实现，避免同一份数据在两页出现两种次序。

### 8.8 目标平台（Windows / Linux）

- 生成客户端部署包时必须选择**目标平台**：`Windows x64`（默认）、`Linux x64`、`Linux ARM64`。平台决定包内 `frpc` 用哪一份二进制、脚本用哪一套模板、文本文件行尾与 BOM 怎么归一。
- **可选清单由后端下发**（`/api/pkg/meta` 的 `client_platforms`），取决于这份平台 exe 里**实际内嵌了哪些二进制**；前端不硬编码。漏拷二进制时该平台根本不会出现在下拉里，而不是选了之后才在目标机器上炸。
- 目标平台是**这一次出包**的属性，不是客户端的属性：同一 `clientID` 可以先出 Windows 包再出 Linux 包，台账与端口冲突判定都不区分平台 —— 远端端口是 frps 上的全局资源，与客户端跑在什么系统上无关。
- **平台自身部署包与服务端部署包仍然只有 Windows**：前者依赖计划任务、`NTFS` ACL 与 DPAPI（凭据加密机器绑定），后者面向的 frps 主机已确认是 Windows。不随本项能力一起开放。
- 两个平台的脚本是**并列的两套模板，不是一套模板加分支**。机理毫无共同点（计划任务 vs systemd；PowerShell 5.1 需要 BOM 才能正确读中文 vs shell 有 BOM 就找不到 `#!/bin/sh`），强行共用只会让模板塞满分支，而分支正是「改一处漏一处」的入口。但**语义必须逐条对齐**：
  - 只操作本部署目录的实例：Linux 侧靠 `/proc/<pid>/exe` 符号链接精确比对可执行文件绝对路径（等价于 Windows 侧比对 `Win32_Process.ExecutablePath`），并容忍路径后的 `" (deleted)"` 后缀（二进制被替换后内核会加此标记，不认它会导致升级后「停止无效、两个实例并存」）。**禁止 `pkill -f` / `pgrep -f`** —— 按命令行片段匹配会命中同一台机器上别的 frp 部署，直接打断人家的隧道（F14）。
  - 哈希校验两级不对称（主程序不符致命 / 配置不符只警告），与 §8.3 同一套理由。
  - 停止先 `SIGTERM` 并等待，超时才 `SIGKILL` 且必须告警。
  - 自启是「兜底重试，不是守护进程」：Windows 侧 `RestartCount=3`，Linux 侧必须显式 `StartLimitBurst=3` —— **systemd 默认是无限次重启**，不显式限流会把一个起不来的服务反复拉起、日志刷屏并掩盖真实故障。
  - 退出码沿用同一套约定（0/1/2/10/11/12/13），便于监控跨系统用同一套判据。
- 文本文件的行尾与 BOM **按平台分别归一，不统一**：Windows 包 `BOM + CRLF`；Linux 包**一律无 BOM + LF**（`.sh` 带 BOM → 内核找不到 `#!/bin/sh`，报「No such file or directory」；CRLF → `bad interpreter`；unit 带 BOM → systemd 语法错误。三者都不指向真正的原因）。`frpc.toml` / `frps.toml` 两平台都不能带 BOM（FRP 严格解码）。
- Linux 包的可执行位在 ZIP 里按 `0755` 写入，但部分解压工具不还原，包内 `README.txt` 必须保留 `chmod +x` 的兜底说明。
- Linux 脚本用 **POSIX `sh`** 而不是 bash：Alpine 与部分最小化镜像没有 bash，而本套脚本没用到任何 bash 专有语法。
- Linux 侧要求 root，但**不静默调 sudo**（sudo 需要交互输入密码，脚本里悄悄调起只会让无人值守的安装挂在一个看不见的提示上）；检测不到 `systemctl` 就直接报错退出，不留一个「装完了却没启动」的包 —— 后者会让运维往完全错误的方向查。

### 8.9 改包：从台账重建出包表单（F27）

- **「编辑旧包」不存在。** 部署包 ZIP 从不落盘、服务端也不保留签发时的密钥（§8.5 的刻意取舍），所以物理上拿不到那份旧包。能重建的只有**当初的输入**，而它唯一的去处是客户端台账。因此改包的正确形态是：用台账内容重建一张表单 → 管理员在上面改 → 走原有的签发路径产出一个**新**包。新包与旧包共用同一个 `clientID`，目标机器上覆盖安装即可，不需要重新登记，也不会丢历史。
- **台账必须存够「下一次出包所需的全部输入」，否则这个功能悄悄退化。** 为此 `client_registry` 增加 `platform` 列（迁移 v4），含义是**这条记录最近一次出包的目标平台**。空串表示该记录签发于支持平台记录之前 —— 那时几乎全是 Windows，但改包必须让它回落到默认平台并**同时给出告警让管理员确认**：平台是唯一一处「猜错会导致包根本装不上」的字段（给 Linux 盒子出 Windows 包，安装脚本不会报错，症状要等上线才发现）。
- **这条值最容易被一次无关操作清掉。** 台账编辑接口是「整体替换」语义，调用方漏传 `platform` 就把它清成未记录。事故链条是：某天点了一次「停用/启用」→ 几周后给这台 ARM 盒子改包 → 产出 Windows 包。因此停用、启用、改类型三条路径都要把它原样带上，回归里对这三条路径各有一条断言。
- **表单里的值必须在界面上分成两类，不许混着展示**：台账里有的（真实还原）与台账里没有的（按默认值补齐）。第二类的危险在于它长得和第一类一模一样 —— 「日志级别」这种填了无妨，而「连接 token」「HTTP 绑定域名」「STCP 访问密钥」填错就是线上故障。因此后端在响应里如实回 `defaults_applied`（整包级）与 `proxy_defaults`（逐条代理列出缺哪些字段，只列这条代理类型用得上的：给 tcp 列 `custom_domains` 是噪音，给 http 不列才是漏），前端据此渲染一块「这些不是原包的样子」的提示。
- **连接 token 永远取自当前客户端接入点，不试图还原旧包的。** 一是旧包的 token 从未留存；二是就算留着也必须与接入点一致 —— 两端 token 不一致时目标机器上的 frpc 连不上，而这个故障在管理台这一侧看不到任何痕迹。接入点读不出来（典型是 DPAPI 密文随 SQLite 换了机器）时降级为空值让管理员手填，而不是把整台设备的改包入口废掉。
- **改包走的是原签发路径，所有规则对它一样生效**：端口冲突照样拦（含实时在线口径）、FRP 校验照样跑、生成审计与 `pkg_record` 照样写、台账照样按新表单更新。唯一放宽的一处是**冲突判定要排除这台设备自己占用的端口**（`ownerClientID`） —— 改包的典型动作就是「同一台设备、同一批端口，再出一版」，不排除则首次签发之后再也发不出第二版，而这是改包唯一会走的路径。
- **台账页每行提供「生成包」入口**，跳转只带台账 `id`（`/packages?from=<id>`）：spec 里含 token，放进地址栏等于把密钥写进浏览器历史与截图。目标页面按 `id` 自己取草稿，取到后再打开弹窗（顺序反了会先闪一版全新默认值）；取不到就退回「新增」并提示，而不是把管理员卡死 —— 那条记录可能刚被删。

## 9. 明确不做的范围

- 不修改、不重新编译、不 fork `frps.exe` 或 `frpc.exe`。
- 不替代 FRP 的数据转发；管理平台故障不得中断现有隧道。
- 首版不管理多台 frps，不做公网 SaaS、多租户计费或复杂权限系统。
- 不提供任意远程命令、远程桌面或客户端文件浏览功能。
- 不在首版从后台直接重启远程 frpc；生成和监控是主要边界。
- 不自动打开公网防火墙端口；只在说明中列出管理员需要放行的端口。
- 不默认使用随现有目录提供的旧 `nssm.exe`。
- 不保证兼容所有历史 FRP 版本；正式支持 `0.69.x` 与 `0.71.x`（2026-09-25 起），其他版本需经兼容测试。
  支持范围是一个**集合而不是单个版本线**：frps 与平台内嵌的 frpc 是两份独立分发的二进制，
  升级只能分批做，过渡期两端版本必然不一致（实测可混跑，见 `03-frp-api-contract.md` §0）。
- 当前不规划多节点、长期历史指标、复杂趋势图表和消息告警。

## 10. 依赖、假设与风险

### 10.1 外部依赖

- FRP `0.69.x` / `0.71.x` Windows AMD64 二进制及其 Dashboard API（平台内嵌 0.71.0）。
- Windows 10/11 或 Windows Server 2019 及以上。
- PowerShell 5.1 或更高版本、任务计划程序服务可用。
- 管理平台主机对 FRP Dashboard 的本机访问权限。

### 10.2 待确认假设

- 【待确认】首版管理平台与 frps 部署在同一台 Windows 主机。
- 首版及当前后续规划只管理一个 frps 节点。
- 【待确认】客户端和服务器均以 Windows AMD64 为首发平台。
- 【待确认】自启动默认采用“Windows 计划任务”，而不是继续使用现有 NSSM。
- 【待确认】管理后台先支持中文，暂不做多语言。

### 10.3 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| FRP Dashboard API 跨版本发生变化 | 升级 FRP 后监控失效 | 建立版本探测与适配层；正式支持版本写入兼容矩阵 |
| 生成包泄露 token 或密码 | 未授权客户端接入 | 即时生成、不持久化 ZIP、日志脱敏、下载审计、强随机密钥 |
| API 与管理台直接暴露公网 | 管理权限泄露 | Dashboard 默认环回监听；管理台默认受登录保护并提示配置防火墙/TLS |
| 计划任务启动后缺少明显日志 | 排障困难 | 固定日志目录、状态脚本、进程与最近日志摘要 |
| 同机存在多个 FRP 实例 | 脚本误停其他实例 | 使用 PID 文件、任务名和完整可执行路径识别实例，不使用全局 `taskkill /im` |
| 远端端口在生成后被占用 | 新客户端代理注册失败 | 生成时预检，安装后检查日志和管理台状态，明确冲突错误 |

## 12. 验收主路径

1. 在服务器上安装并启动 SinyeFRP 管理平台。
2. 首次打开后台，创建管理员并连接本机 `frps` API。
3. 总览正确显示 FRP 版本和当前客户端数量。
4. 在客户端生成页面填写名称、服务器地址和一个 TCP 代理。
5. 下载 ZIP，在另一台 Windows 机器解压并以管理员身份运行 `install.ps1`。
6. 管理台在一个采样周期内显示新客户端在线，并展示对应代理。
7. 重启客户端 Windows，确认无需登录即可重新上线。
8. 运行 `status.ps1` 和 `restart.ps1`，确认状态与管理台一致。
9. 运行 `uninstall.ps1`，确认自启动任务被移除且配置和日志仍保留。
10. 停止 frps 或输入错误 API 密码，确认管理台显示节点未知/认证失败，而不是将所有客户端错误标为离线。
